### **Решение**
Архитектурное решение основано на принципах микросервисной архитектуры с сохранением интеграции с существующими системами банка.

#### Ключевые архитектурные принципы:
1. **Изоляция от АБС**: Новые сервисы не имеют прямого доступа к АБС, используется асинхронная интеграция
2. **Микросервисная архитектура**: Депозитный функционал выделен в отдельные сервисы
3. **API Gateway**: Единая точка входа для всех клиентских запросов
4. **Event-Driven Architecture**: Использование событий для интеграции между сервисами

#### Основные компоненты решения:

**Уровень представления:**
- **Веб-интерфейс сайта**: React.js приложение для новых клиентов
- **Интернет-банк (модернизированный)**: Добавлен депозитный модуль на ASP.NET

**Уровень сервисов:**
- **API Gateway**: Маршрутизация запросов и авторизация
- **Deposit Service**: Микросервис управления депозитными заявками
- **Rate Management Service**: Микросервис управления ставками депозитов
- **Notification Service**: Микросервис уведомлений (СМС, email)
- **Integration Service**: Сервис интеграции с АБС

**Уровень данных:**
- **Deposit Database (MS SQL)**: База данных заявок на депозиты
- **Rate Database (MS SQL)**: База данных ставок
- **Redis Cache**: Кэширование ставок и пользовательских данных

**Интеграционный уровень:**
- **Message Queue (Kafka)**: Асинхронная обработка событий
- **Batch Integration**: Ежедневная синхронизация с АБС

#### Диаграммы:
- [C4_Context.puml](context_C4.puml)
- [C4_Containers.puml](context_C4.puml)

#### Технологический стек:
- **Frontend**: React.js, HTML5, CSS3
- **Backend Services**: ASP.NET Core, Java Spring Boot
- **Databases**: MS SQL Server, Oracle (для АБС)
- **Cache**: Redis
- **Message Queue**: Apache Kafka
- **API Gateway**: ASP.NET Core Gateway или Kong
- **Monitoring**: ELK Stack (Elasticsearch, Logstash, Kibana)

#### Логика принятия решений:

**Выбор микросервисной архитектуры:**
- Требование изоляции от АБС (+R6)
- Необходимость независимого масштабирования депозитного функционала
- Возможность независимой разработки и развертывания

**Использование API Gateway:**
- Централизованная авторизация и аутентификация
- Единая точка мониторинга и логирования
- Возможность маршрутизации запросов между legacy и новыми сервисами

**Асинхронная интеграция с АБС:**
- Защита критичной системы от перегрузки
- Соответствие техническим ограничениям (batch-интеграция раз в день)
- Возможность обработки пиковых нагрузок через очереди

**Сохранение существующих технологий:**
- MS SQL для новых сервисов (соответствие +R1)
- ASP.NET для интернет-банка (использование существующей экспертизы)
- Oracle для АБС (сохранение текущей архитектуры)

### **Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

#### Альтернатива 1: Монолитное расширение интернет-банка
**Описание**: Добавление депозитного функционала непосредственно в существующий монолит интернет-банка без выделения микросервисов.

**Преимущества**:
- Простота реализации
- Меньше точек отказа
- Использование существующей инфраструктуры

**Недостатки**:
- Нарушение требования микросервисной архитектуры (+R3)
- Сложность независимого масштабирования
- Риск влияния на существующий функционал

#### Альтернатива 2: Прямая интеграция с АБС через API
**Описание**: Создание прямых API-интеграций между новыми сервисами и АБС для real-time обработки.

**Преимущества**:
- Мгновенная обработка заявок
- Меньше сложности в архитектуре
- Отсутствие необходимости в очередях сообщений

**Недостатки**:
- Нарушение требования изоляции от АБС (+R6)
- Риск перегрузки критичной системы
- Техническая невозможность (АБС не поддерживает API)

#### Альтернатива 3: Использование внешней cloud-платформы
**Описание**: Развертывание новых сервисов в публичном облаке (AWS, Azure) вместо собственной инфраструктуры.

**Преимущества**:
- Автоматическое масштабирование
- Высокая доступность
- Современные технологии

**Недостатки**:
- Нарушение требования использования существующей инфраструктуры (+R13)
- Вопросы безопасности и комплаенса
- Дополнительные затраты на облачные сервисы

**Недостатки, ограничения, риски**

#### Недостатки выбранного решения:

1. **Сложность архитектуры**: Микросервисная архитектура увеличивает сложность разработки, тестирования и эксплуатации

2. **Eventual Consistency**: Асинхронная обработка может привести к временной несогласованности данных между системами

3. **Латентность**: Дополнительные слои (API Gateway, микросервисы) могут увеличить время отклика

4. **Операционные накладные расходы**: Необходимость мониторинга и управления множественными сервисами

#### Ограничения:

1. **Batch-интеграция с АБС**: Ограничение обмена данными с АБС до одного раза в день

2. **Совместимость технологий**: Необходимость использования только MS SQL и Oracle

3. **Инфраструктурные ограничения**: Развертывание только в существующих ЦОД банка

4. **Регуляторные требования**: Соответствие требованиям ЦБ по идентификации клиентов

#### Риски:

1. **Технический риск**: Сложность интеграции между микросервисами может привести к задержкам в разработке

2. **Операционный риск**: Увеличение количества точек отказа в системе

3. **Производительностный риск**: Возможность не достижения целевого времени отклика < 100 мс

4. **Безопасностный риск**: Увеличение поверхности атаки из-за множественных API endpoints

5. **Масштабирования риск**: Необходимость горизонтального масштабирования может потребовать дополнительных инвестиций в инфраструктуру

#### Меры по снижению рисков:

1. **Поэтапная миграция**: Начало с MVP функционала для снижения сложности
2. **Comprehensive monitoring**: Внедрение детального мониторинга всех компонентов
3. **Circuit breaker pattern**: Использование паттернов устойчивости для предотвращения каскадных сбоев
4. **Load testing**: Тщательное тестирование производительности перед продакшеном
5. **Security by design**: Встроенная безопасность на всех уровнях архитектуры
